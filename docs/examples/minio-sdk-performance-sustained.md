# 持续写入与有界分片调度验证

最新定位与复测见[写入波动定位报告](minio-sdk-write-diagnosis.md)。

## 执行

- 本地 MinIO RELEASE.2025-02-03T21-03-04Z；容器 4 CPU / 2 GiB，HTTP 回环。
- AWS C++ 1.11.675 与 MinIO C++ 1.0.0，各 4 个独立客户端，1 轮预热、4 轮正式测量。
- 执行全部性能用例：多对象、重复访问、三种小对象读取、三种 Range 大小×三种模式、四种分片组合。
- 基础多对象输入：100×128 KiB + 64×4 MiB；重复对象 8 MiB、每项至少 100 次；分片每组至少 2 个对象，不足 5 秒自动写入新 Key。
- 正式样本 36,264；全部样本 41,524，失败 0；执行错误 0；对象与未完成分片全部清理。耗时 545.4 秒。

## 窗口与 I/O

48 个正式写窗口全部满足 5 秒，最短 5.028 秒。临时目录文件系统为 `ext4`，没有默认使用 tmpfs；输入逐文件 fsync 后计时。
窗口内所有客户端进程合计的实际磁盘读取最多 0.000 MiB、写入最多 0.000 MiB。这里是 /proc 计数，不是 SDK 传输量；已记录主机 Dirty/Writeback、I/O pressure 和分设备计数，不能仅凭主机指标归因远端存储。

分片执行器最多提交 4 个在途任务，轮流选择就绪对象；不再一次预提交整个对象的全部分片。每个请求保留调度等待、执行器派发等待、客户端等待、RPC wall 与 SDK 时间。

## 本地资源对照

完整 48 个窗口复核后，MinIO 容器累计 CPU 限流约 3.9 ms；服务端 cgroup 的 I/O some 等待占比约 0.54%–9.33%。这些计数不支持把数倍吞吐差异简单归因于 CPU 配额，也不能单独证明存储内部的具体瓶颈。

另用相同 AWS C++ SDK、4 客户端、4 CPU、大块 PUT 用例，仅把 MinIO 内存上限从 2 GiB 改为 4 GiB，各测 4 轮：

| MinIO 内存上限 | 汇总 MiB/s | 四轮 CV | 内存 some 等待占比 |
|---|---:|---:|---:|
| 2 GiB | 172.62 | 47.3% | 0.02%–0.11% |
| 4 GiB | 96.56 | 24.6% | 0% |

4 GiB 下不再触发内存上限，但仍明显波动，吞吐没有改善；本次对照不支持把增加内存作为解决办法。两组先后执行，不能据此断言较大内存导致变慢。代码继续使用普通磁盘临时文件；没有新增 RAM 缓存、内存模型或必填参数。对照原始证据在 `results/minio-memory-control-20261022/`。

## 正确性与回归

- 所有自动新增 Key 均在写计时外进入生产读回、内容校验与清理，不混入后续固定集合的 GET/Range/LIST/HEAD 测量；错误完成会真实 Abort，未验证对象及其分片有效字节归零。
- 129 项框架回归：127 项通过、2 项可选构建测试跳过。
- 4 项真实 MinIO Java/C++ SDK 集成回归通过，包含自动延长窗口。
- 六种故障注入均被回归检出：移除文件同步、关闭持续 PUT、放宽执行器上限、恢复偏置顺序、取消高波动判定、把额外 Key 混回固定读取集合。恢复后相关测试通过。

本次仍有写入波动，根因尚未定位；高波动结果保留为不确定，不提供稳定 SDK 排名。

本次 SDK 组合、轮数和持续工作量与旧报告不同，不能直接将汇总吞吐差异解释为 SDK 或存储提速。原始配置、样本与观测在本地 `results/minio-sdk-sustained-final-20261022/`，包括 `write-window-evidence.json`。
