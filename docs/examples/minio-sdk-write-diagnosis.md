# MinIO 写入波动定位与修复

## 定位结果

服务端采样已确认两个来源：同 Key 并发覆盖的对象锁争用，以及独立对象写入的数据文件同步落盘等待。清理旧回归测试遗留的单核忙循环后，单独写入仍能复现波动。

### 热点覆盖争用

原有 `repeat_put` 的所有并发通道写同一个 Key。MinIO 该版本使用对象锁，获取失败后随机等待最多 50 ms 再试，见[对应版本源码](https://github.com/minio/minio/blob/RELEASE.2025-02-03T21-03-04Z/internal/lsync/lrwmutex.go#L94-L120)。

相同 MinIO C++ SDK 的两轮诊断中：

| 吞吐 | PUT Handler 采样中等待对象锁的比例 |
|---|---:|
| 846.9 MiB/s | 16.6% |
| 359.8 MiB/s | 44.7% |

等待栈为 `PutObjectHandler → putObject → LRWMutex.lockLoop → time.Sleep`。这些比例按所有 PUT Handler 的累计采样时间计算，包含并发请求，不能理解为单个请求或程序墙钟的精确占比。该用例衡量热点覆盖争用，不能独自代表独立对象写入性能。

### 独立对象落盘等待

相同 MinIO C++ SDK、多对象独立 Key、4 MiB 对象、4 个客户端的诊断结果：

| 吞吐 | PUT Handler 等待写入器关闭的比例 | 数据写入协程的 Fdatasync 累计采样时间 |
|---|---:|---:|
| 431.5 MiB/s | 55.2% | 9.07 协程秒 |
| 149.4 MiB/s | 84.9% | 16.04 协程秒 |

请求处理协程等待 `streamingBitrotWriter.Close → WaitGroup.Wait`，数据写入协程停在 `xlStorage.writeAllDirect → Fdatasync`。4 路并发的等待会重叠，因此约 5 秒窗口内累计协程时间可以超过 5 秒；父协程和写入协程的时间不能重复相加。

独立 Key 的对象锁等待接近零。吞吐下降时主要增加的是数据文件同步等待；目前定位到服务端落盘阶段，尚未进一步拆分内核和设备内部耗时。

诊断使用相同版本 MinIO、4 CPU / 2 GiB、同机磁盘绑定目录，并开启服务端 CPU+I/O profiling。下方正式复测关闭 profiling、使用原磁盘卷环境；诊断中的吞吐仅用于对应调用栈。

### 分片上传

128 MiB 对象、16 MiB 分片的两轮 AWS C++ 诊断也复现相同位置：

| 吞吐 | UploadPart Handler 等待写入器关闭的比例 | Fdatasync 累计采样时间 |
|---|---:|---:|
| 361.8 MiB/s | 77.7% | 15.74 协程秒 |
| 906.8 MiB/s | 47.5% | 8.36 协程秒 |

等待栈为 `PutObjectPartHandler → PutObjectPart → streamingBitrotWriter.Close`；数据协程仍停在 `Fdatasync`。这将分片的波动也对应到服务端数据落盘阶段，并非仅从总吞吐猜测。

## 工具修复

- 保留 `repeat_put` 热点场景，自动增加 `parallel_put`：每个通道一个独立 Key，复用磁盘输入，无需额外配置。
- 两种覆盖写在上传计时结束后，真实 GET 各 Key，校验最终长度与完整 SHA-256。失败时该 Key 对应写样本全部失败、有效字节归零。覆盖写只校验最终状态，不宣称逐个验证历史覆盖版本。
- 独立通道 Key 在计时外删除，保持后续 GET、HEAD、LIST 的固定对象集合。
- 多对象与重复访问保留每个请求的开始、结束及驱动往返时间，报告可对照 SDK 与驱动往返 p95，区分进程通信开销。
- 临时输入和正式 MinIO 数据继续使用磁盘，没有新增内存数据集或性能档位。

## 正式复测

MinIO `RELEASE.2025-02-03T21-03-04Z`，4 CPU / 2 GiB，HTTP 回环；AWS C++ `1.11.675` 与 MinIO C++ `1.0.0`，各 4 个客户端。1 轮预热、4 轮正式测量，全部性能用例自动执行。

正式样本 **35,234**；全部样本 40,694，失败 0、执行错误 0；对象与未完成分片全部清理。耗时 583.0 秒。

多对象输入为 100×128 KiB + 64×4 MiB；重复对象 8 MiB、每项至少 100 次请求。三种小对象读取、三种 Range 大小×三种模式全部执行。分片为 32/128 MiB 对象×5/16 MiB 分片，每组至少 2 个对象，写窗口不足 5 秒自动延长。

56 个正式写窗口均满足 5 秒，最短 5.014 秒。热点与独立通道的所有最终状态读回均通过。

| 用例 | AWS MiB/s | MinIO MiB/s | AWS CV | MinIO CV |
|---|---:|---:|---:|---:|
| 多对象 PUT | 271.76 | 347.13 | 45.4% | 40.1% |
| 每通道独立 Key 覆盖写 | 247.57 | 218.77 | 24.3% | 29.1% |
| 同 Key 热点覆盖写 | 249.09 | 301.22 | 23.1% | 31.4% |
| 分片 32 MiB / 5 MiB | 424.40 | 245.44 | 57.7% | 48.1% |
| 分片 32 MiB / 16 MiB | 303.53 | 311.77 | 45.6% | 52.4% |
| 分片 128 MiB / 5 MiB | 224.52 | 253.02 | 58.6% | 82.0% |
| 分片 128 MiB / 16 MiB | 398.52 | 371.60 | 51.7% | 49.5% |

所有具有双重计时的正式请求中，驱动往返减 SDK 时间的中位数为 0.110 ms，p95 为 0.224 ms。多对象 PUT 的 SDK 与驱动往返 p95 分别为 AWS 358.17/358.27 ms、MinIO 316.89/317.02 ms。进程通信额外耗时远小于观察到的数百毫秒写入停顿。

**波动仍然存在，不能据此给 SDK 稳定排名。** 工具已补齐独立 Key 对照、最终状态校验与请求墙钟证据；服务端采样将主要等待定位到对象锁或磁盘同步。尚未进一步拆分内核与设备内部的同步耗时。

正式原始配置、样本和逐轮资源观测在本地 `results/minio-sdk-contention-fixed-20261022/`；服务端原始 profile、诊断请求和校验摘要在 `results/minio-write-profiles-20261022/`。Profiling 是本地诊断手段，没有加入通用 S3 用例或配置项。

## 回归

- 134 项框架回归：132 项通过、2 项可选构建测试跳过。
- 真实 MinIO Java/C++ SDK 集成测试通过，覆盖独立 Key、持续写入、读回和清理。
- 五种故障注入均被回归检出：通道错误共用 Key、跳过最终读回、忽略内容摘要、保留损坏对象字节记账、取消独立 Key 清理。源码恢复后通过。
- 边界包含单通道、请求数少于通道数、非整除请求数、等长/不同长度损坏、GET 失败时已有正确旧文件，以及一次 PUT 失败后后续覆盖成功。
